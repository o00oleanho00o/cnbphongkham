# Prototype review findings and regression cases

Read-only review of the shared prototype on 20 September 2026. Findings below describe checks the owner should rerun after builder changes. They use synthetic data only; no patient record or clinic login was accessed. The original storage/shape failures were historical observations; the current authoritative result is `demo-assets/test-results/data-audit.json`, generated by the runnable `prototype/data-audit.cjs` script.

## Regression checks to run

### 1. Storage failure must not blank the app

The data layer persists the initial dataset and uploaded image data in `localStorage`. A browser quota/security failure currently makes the initial save throw, and a few 2.5 MB images become larger base64 strings when stored. Verify that the UI remains usable and shows a clear demo-storage error (or falls back safely) when `getItem`/`setItem` throws. Also verify that a malformed or incomplete `version: 2` object is rejected and reset instead of causing `Pema.patient()` to read `undefined`.

Suggested Node smoke check (from workspace root; this is not a production test):

```powershell
@'
const fs=require('fs'),vm=require('vm');
const src=fs.readFileSync('prototype/shared/data.js','utf8');
for (const [name,storage] of [
  ['storage throws',{getItem(){throw Error('SecurityError')},setItem(){throw Error('QuotaExceededError')}}],
  ['empty v2',{getItem(){return '{"version":2,"patients":[]}'},setItem(){}}]
]) { try { const c={localStorage:storage,window:{dispatchEvent(){},addEventListener(){}},Event:class{}}; vm.runInNewContext(src,c); c.window.Pema.patient(); console.log(name,'SAFE'); } catch(e) { console.log(name,e.name,e.message); } }
'@ | node -
```

Expected result: neither case produces an uncaught render-time exception.

### 2. New patient must start independent

Create a new patient after opening an existing patient with alerts, medications, events, photos, and consent set to false. Confirm the new record has its own neutral defaults: no inherited events/messages/invoices/sessions, no inherited treatment plan or aftercare, no inherited alerts, and consent is not silently shown as approved. Reopen the new record and then the original to confirm there is no shared mutable array or object.

### 3. Invalid patient identity must be visible and safe

Set `pema-patient-identity` to `P999` (or malformed JSON) in the patient app's local storage, reload, and confirm the app selects a documented demo fallback or displays a clear “hồ sơ không tồn tại” state. It must never silently show P001 while the header, messages, or consent state imply that the requested identity was loaded.

### 4. Appointment consistency across apps

From Clinic Today, book or edit a future appointment for a non-P001 patient. Open Patient Mobile with that identity. The date, time, doctor and concern shown in Home/Appointments must match the clinic record. Confirming attendance should append one event/message only; repeated clicks should be idempotent or clearly disabled.

### 5. Draft and upload retention during cross-app updates

On Patient Mobile, type a message and select a file without submitting. Trigger a `pema-change`/storage update from the clinic window (or use another tab), then return to the form. The unsent text and selected-file state should be preserved or the UI should warn before replacing it. Repeat with a clinic consultation draft. Do not silently erase clinician/patient input on an external render.

### 6. Follow-up resolve and reply integrity

Submit a patient update with and without a photo. In Clinic Follow-up Inbox, resolve each item once. Verify: status changes from open to resolved; the reply is appended to the same patient's messages; a timeline event contains the actual follow-up type and text; the inbox count decreases; and resolving again does not duplicate the reply/event. Urgent symptoms must remain a human-review/escalation message and must not be phrased as an AI diagnosis or automatic clearance.

### 7. Session and photo behavior

Save a treatment session with a note and consent. Verify session count, date, type, note, timeline event and Patient Mobile journey update. Save without a photo and confirm the resulting missing-photo follow-up is visible. Try an invalid file type and a file over the stated limit; no partial session should be created. The Before/After “Thêm ảnh” action must either open a real, validated input flow or state clearly that capture is unavailable; it must not be a silent dead button.

### 8. Ask Pema and KPI truthfulness

Reset the deterministic data and compare every dashboard/today KPI to a direct count of the same state (appointments for the displayed date, waiting patients, open follow-ups, running plans). Ask each sample question after creating/resolving a follow-up and check that the answer changes, names only real IDs, and links to a source queue. Verify no hardcoded “42” or stale patient names remain. Today’s waiting alert must display the computed count.

### 9. Filters and keyboard path

On Today, Patients and Follow-up Inbox, click every visible filter and confirm the rows/counts change or the control is explicitly labelled as a non-functional demo. Tab through the flow on a 375 px viewport: sidebar access must have an alternate mobile menu; patient-app cards/links and hidden file inputs must be keyboard reachable; focus rings must remain visible; dialogs must have a labelled heading and a usable close button. Check that tables and follow-up cards do not require accidental horizontal scrolling.

### 10. Synthetic-data and clinical-language guardrail

Confirm all images retain the “MINH HỌA TỔNG HỢP”/synthetic disclaimer, no real patient identifiers are present, and AI copy remains “bản nháp — bác sĩ duyệt.” Patient-facing content must direct urgent or worsening symptoms to the clinic's human process and must not claim a diagnosis, treatment efficacy, or emergency service.

## Evidence captured during review

- `node --check` passed for `prototype/shared/clinic.js`, `patient.js`, and `data.js` before the latest builder edits.
- The first VM check reproduced an uncaught `QuotaExceededError` at initial persistence and a `TypeError` for an empty `version:2` state. Those findings are historical and were subsequently addressed in `data.js`; rerun `node prototype/data-audit.cjs` before relying on them.
- The app uses `localStorage` key `pema-demo-v2` for shared clinic/patient state and `pema-patient-identity` for the patient selector. Keep those identities explicit in cross-app screenshots and test notes.
